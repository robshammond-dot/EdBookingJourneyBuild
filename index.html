03The Mechanism

Journeys, not Sequences

Journeys are the fit Freshsales Sequences are capped at 90 days (Classic) or run on repeating intervals (Smart), fine for something like the Quoted Follow Up cadence, but not built for a 12-month span. Freshmarketer Journeys already run for months at a time with no such cap, the New Subscriber Journey checks in every 4 weeks across three sends, the Lost Journey spans 8–12 week gaps across four. That's already proven at Edusport, so this is very likely one Journey structure reused across all four windows (Long/Medium/Short/Post-Travel), not a Sequence, and not a mechanism that needs to differ by window.

Building blocks, in order

  • Snapshot at Won — when an Enquiry is marked Won, tag the Contact into an event + window segment, e.g. Booking Journey – Abu Dhabi GP – Medium. This is what the Journey's entry condition reads.
  • Booking Date / Travel Date mirrored to Contact — still needed to anchor entry timing and calculate which window (Long/Medium/Short) the booking falls into, mirrored from the Enquiry, same pattern as the existing pipeline-stage sync.
  • Status re-check per step — the existing Lost Journey already re-checks its condition before every send, "is the lost reason still current", exiting if not. The Booking Journey can use the same pattern: re-check the Enquiry is still Won and not Cancelled immediately before each send. A full-group cancellation then naturally stops the series at the next step, without necessarily needing a separate real-time removal workflow. Worth testing whether that timing is tight enough, or whether an instant removal is still wanted on top.
  • Destination content, static per event — written directly into the templates, not synced as a field. Only works cleanly for Tier 1 evergreen events, see the Rollout Schedule below.

04Things Worth Deciding Together

The calls that shape the build, not the build steps themselves

What Fresh reliably knows about a booking

Event Name is a multiselect field, so it doesn't get overwritten, older events stay in the list, but it stops being the primary or most obvious one to read off once a new enquiry comes in. Travel Date does get genuinely overwritten, along with the customer status, whenever a new enquiry arrives, that's deliberate, handled by workflows, and exists to keep active quoting and status correct for whatever the customer's current enquiry actually is, not an oversight. Whatever anchors the Journey timing needs its own way of pointing at the right trip, rather than assuming the live Contact fields always will.

Cancellations are already distinguishable

Cancellation is captured as a Lost Reason on the Enquiry, so a cancelled-after-Won customer can be told apart from a pre-booking Lost. One traveller dropping out of a group booking isn't an issue in itself, fine for the rest of the party to keep receiving the series. What does need handling is the whole booking cancelling after the group was already added to the event segment, see the status re-check pattern above.

Past bookings, people already confirmed before this goes live

Window classification (Long/Medium/Short) is based on time-to-travel, not time-since-booking, so it calculates the same way for an existing customer as a new one, that part isn't the problem. The real issue is where they'd join the series: entering a Journey that runs linearly from Mailer 1 would send someone who booked months ago a "Congratulations, you're officially booked!" open, months late and out of step with the relationship they already have with their consultant.

Two options, worth a decision rather than assuming either:

  • Exclude past bookings from the pilot — only Enquiries marked Won after the Journey goes live get tagged into the segment. Existing Abu Dhabi bookings stay untouched. Cleanest for a first pilot.
  • One-time backfill — identify existing Won, not-cancelled Abu Dhabi bookings, calculate current time-to-travel, and enter each one at whichever mailer actually matches today, skipping earlier ones rather than starting at Mailer 1. More complete, but extra one-off work, and needs the Journey steps built so someone can join partway through.
Open product question, not yet decided Which of the two above for the Abu Dhabi pilot, exclude past bookings or backfill them mid-series? Leaning toward excluding for a first pilot, keeping it simple, but this is a call for the team, not something to assume.
Open product question, not yet decided What happens when a repeat traveller books a genuinely second, separate trip while their first Booking Journey is still running? A second, parallel journey, or excluded while the first is active?

05Rollout Schedule

Tier 1 evergreen events, ordered by date, from today (4 August 2026) using the Product Development Dates sheet

Why Abu Dhabi GP works as the first demo Abu Dhabi GP runs 3–6 December 2026 (per the official Ethara/abudhabigp.com listing, worth confirming against the 04–06 December on the Product Development Dates sheet). It's a well-known, high-profile Grand Prix on a fixed venue, evergreen content, low risk to get destination copy right, and its Medium-window timing today makes it a manageable first build to prove the segment and content approach on.

Ordered by date and evergreen tier, not by booking volume, volume by event isn't something we have visibility on yet (Micro Marketing Planner / Fresh Tags would confirm that). Worth cross-checking this order against actual demand before committing beyond the pilot.

Suggested phased rollout

  • Phase 1 · Pilot — Abu Dhabi GP, Medium window content only. Proves the segment/status-recheck logic and the destination content approach on one event before anything else touches it.
  • Phase 2 · Expand within Medium/Short — once the pilot is stable, roll the same content structure out to the other Tier 1 Grand Prix and MotoGP rounds above.
  • Phase 3 · Extend to the Long window — once Medium/Short content is proven, extend the same Journey approach to events that sell 9–12 months out (e.g. Australian Open, Wimbledon, French Open, and Grand Prix/MotoGP rounds early in the 2027 calendar). Sequenced last mainly so content and destination copy get proven on a smaller scale first, not because the mechanism is harder, since Journeys don't have a duration constraint to work around.
Worth checking before locking this in This list is Tier 1 evergreen events only, chosen for venue stability, not for how many people actually book them. If a lower-tiered or rotating-venue event (Tier 2, e.g. a Champions League Final) is actually a bigger revenue driver than several of these, that's a reason to slot it in earlier despite the extra content-maintenance overhead, worth a quick sense-check against real numbers.
